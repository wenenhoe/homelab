# Do the generated doc views need to be committed with every change?

The decision index, the planning view and the disaster-recovery coverage table are generated from frontmatter and the app catalog, and each is committed. Every change that adds or moves a decision, a project, an exploration or an app has to commit the regenerated view with it. That cost shows up in three places: the tooling around `git am`, two changes that cannot land side by side, and a rebuilt commit that is not identical to the first build. The question is whether committing them is worth that.

## What bears on it

- [`.githooks/generated-views`](../../.githooks/generated-views) lists the three views. The `generate-doc-indexes` hook rewrites them and fails when it had to, so every commit carries views that match the generator ([`pre-commit.md`](../topics/engineering/pre-commit.md#applying-patches-with-git-am)).
- Patches leave the views out so two series that each add a project or a decision do not conflict on them. `pre-applypatch` regenerates and stages them, `post-applypatch` amends them into the commit, and the replay resets them between layers and applies one patch per `git am` ([ADR 0112 (Landing a patch series)](../decisions/0112-landing-a-series-of-dependent-changes-on-main/revision-001.md)). A plain `git am` of a series that edits one of them stops at the next patch.
- Of the 200 newest merged pull requests when counted, 59 changed at least one view: the planning view in 52, the decision index in 37 and the coverage table in 1. Two changes that add a decision both edit the same table, so a merge of the second can conflict even though the changes share no other file. GitHub's merge refuses a conflicting pull request, and a workflow cannot push a regenerated view to `main`, which accepts only a pull request merged with the Admin bypass.
- The views no longer read git history. The planning view's table of explorations lists the name and question and no date, so the three views are a function of the tree: a rebuilt layer carries the same views as its first build, and the generator needs no history.
- The decision index and the planning view are linked by path from about forty docs, with 16 anchor links into the decision index and 12 into the planning view and none into the coverage table. The project scope rule (`doc_scope.py`) and the progress log's classifier (`classify.py`) also name them by path.
- Readers: the maintainer reads the views on GitHub, including from a phone, and from a checkout. Agents read them from a checkout. A markdown table of four or five columns with long cells is cramped on a phone, so what GitHub renders is readable there only by scrolling sideways.
- A workflow that publishes a site to GitHub Pages needs `pages: write` and `id-token: write` on its deploy job, runs in the `github-pages` environment, and needs the repository's Pages source set to GitHub Actions by hand. It needs no `contents: write`, so it cannot change a branch or a tag. A published site may be at most 1 GB, a deployment times out after 10 minutes, the site has a soft limit of 100 GB of bandwidth a month, and the soft limit of 10 builds an hour does not apply to a custom workflow. The repository is public and the views hold nothing the repository does not, so a public site shows no more than the views already do.
- A workflow triggered on every push to `main` with a concurrency group and `cancel-in-progress: false` has at most one run going and one waiting, and GitHub replaces a waiting run with a newer one, so a burst of merges ends with a run on the newest commit.
- [ADR 0095 (Progress log)](../decisions/0095-recording-what-was-worked-on-each-week-and-month/revision-000.md) describes the progress log's publish job as the one job with a write token, a `contents: write` that pushes to its own branch.

## Options

- **Keep them committed as they are.** Nothing to change. The conflicts, the hook machinery and the phone-sized tables stay, and layers that touch the same view cannot land in parallel.
- **Compare trees without the views.** A scheme that keys a result on a tree, such as reusing a proof of a layer, would leave the three paths out of the key. Heavy checks read none of them. Conflicts remain.
- **Local only.** The views are gitignored and regenerated by `post-merge` and `post-checkout` hooks (git has no pre-pull hook; pre-commit supports those stages) or by running the generator. The conflicts, the apply hooks, the patch rule and the reset between layers all go. A reader on GitHub loses the rendered views and the anchors into them, and every fresh clone needs a generate step. Alone it does not serve a reader on GitHub or a phone.
- **A generated branch.** A workflow on every push to `main`, like `warm-caches.yml`, regenerates the views onto a branch the way the progress log does. They stay rendered on GitHub within a minute or so of a merge. It costs a second job with `contents: write`, a ruleset for the branch made by hand and a short lag. Nothing on `main` could link the views by path. The tables are the same cramped tables on a phone.
- **A published site.** The same workflow, on every push to `main`, builds static pages from the data the generator already holds and deploys them to GitHub Pages. Each view becomes a page that fits the viewport: a table turns into stacked cards on a narrow screen, with a filter by status and topic and a stable URL for each section. The job holds `pages: write` and `id-token: write` and no `contents: write`, so its reach is a deployment and not the repository. It costs a renderer and its tests, a second format for the views to keep in step with their content, the Pages setting made by hand, and a lag of a minute or so. Nothing on `main` could link the views by path, so the links to them, some forty docs and 28 anchors among them, become site URLs or go, which changes what a doc may link to and is a decision. It does not serve a checkout.
- **A published site, with the views not committed.** The site for GitHub and the phone, and the generator run locally for a checkout (by hand, or by the hooks of the local-only option). Every committed view, the apply hooks, the patch rule and the reset between layers go, and both kinds of reader are served. It is the published-site option with the local one beside it.
- **Split each view by entry.** A decision or project would add its own row file, so no two changes share one. The views are one page meant to be scanned, which a directory of rows is not.
- **Regenerate at landing.** The tool would rebase a conflicting layer and run the generator before merging. It makes a new commit and a new tree each time, so any result keyed on the layer's tree is lost unless the views are left out of the key.

## Leaning

The reader question is settled: GitHub, including a phone, and a checkout. That rules out local only on its own and leaves the generated branch and the published site as the ways to serve GitHub without committing the views. The published site is the better of the two: a job that cannot write to the repository, no branch ruleset, and pages that fit a phone, where the generated branch keeps the same tables. Its cost is the renderer and the change to what docs link to. The lean is the published site with the views not committed, with local generation for checkouts, and it can be reached in two steps: publish the site while the views are still committed, so nothing is lost, and stop committing them once the site is trusted. It stays a lean until the checks below are done.

## What has to be checked first

- That the Pages source can be set to GitHub Actions, that the `github-pages` environment accepts a deployment only from `main`, and that `zizmor` and the workflow rules accept a job with `pages: write` and `id-token: write`.
- Whether a Pages site needs a new revision of ADR 0095 or a record of its own: the progress log is described there as the one job with a write token, and the deploy job is a second with a smaller reach.
- Whether anything besides the `generate-doc-indexes` hook, run by `pre-commit-checks` over every file, checks that a committed view is current. If not, dropping the views drops no check.
- What the links from docs to the views become: which of the links, the 28 anchors among them, survive as site URLs, which docs stop naming a view, and what the drift check does with a link to a URL.
- How the project scope rule and the progress log's classifier treat the views once they are not files in the tree.
- How a rendered page is checked on a narrow viewport, since a test of the HTML does not show that a table fits a phone.
- How an agent gets the views in a clone: the generator needs no history now, so `git clone --depth 50` and one command should do.
