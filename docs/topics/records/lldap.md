# lldap: Service Record

The directory that holds the login accounts, on `security`. The container, its certificate renewal and the observer-account bootstrap are in [`lldap.md`](../services/lldap.md). The catalog's facts are in the [coverage table](../disaster-recovery/coverage.md).

## Dependencies

- Needs `step-ca` for its LDAPS certificate (`step_ca_cert`, which also installs the renewal timer), the `data` and `certs` volumes, and its `.env` secrets (admin password, JWT secret, key seed), generated by the `secrets` role.
- Needed by `tinyauth`, which binds to it as the read-only `observer` account; without lldap nobody can log in through Tinyauth. The `lldap_bootstrap` role creates that account right after lldap deploys.

## Data

Holds the user accounts, groups and password hashes in the `data` volume, and its LDAPS certificate in `certs`. The admin password, JWT secret and key seed are secrets; the account passwords are the users' own.

## Exposure

- The web UI is routed through Caddy with `auth: false`, since it is the identity provider and cannot sit behind its own check ([`lldap.md`](../services/lldap.md#one-container-two-host-level-roles)).
- LDAPS (`6360`) is not published on the host. The container carries the certificate's name (`lldap.<caddy_domain>`) as a network alias on `caddy-proxy`, where Docker resolves it, and tinyauth, the one client, binds through that name. Nothing off the host can reach the port.
- Callers authenticate with LDAP bind credentials; the observer account is read-only.
- It keeps `CHOWN`, `SETUID`, `SETGID` and `DAC_OVERRIDE` for its entrypoint ([`adding-an-app.md`](../deploy/adding-an-app.md#container-hardening)).

## Threat model

- The UI has no forward auth, so a weak admin password or an unpatched UI flaw exposes every account. The admin password is generated. Unknown: whether the route is reachable from outside the tailnet; check the Caddy and DNS exposure.
- A reader of the `data` volume gets the password hashes. The volume is backed up encrypted ([`backup.md`](../disaster-recovery/backup.md#encryption)).
- A missing observer group membership silently fails every login; the bootstrap role sets it and is safe to re-run ([`lldap.md`](../services/lldap.md#bootstrapping-the-observer-account)).

## Observability

- Container health and state are in Beszel ([`beszel.md`](../monitoring/beszel.md)).
- The certificate renewer pushes a daily `cert-renewer-lldap` heartbeat, and the backup heartbeats cover the archive ([`gatus.md`](../monitoring/gatus.md)).
- Unknown: whether a failed login path alerts anyone. Check Tinyauth's log level and any Beszel alert rules.

## Disaster recovery

Not tier 1, but backed up: `data` and `certs` at the default schedule ([`backup.md`](../disaster-recovery/backup.md)). It was restored with `tinyauth` on 2026-11-02, on the rebuilt `security`; that drill did not enumerate the users and groups afterwards ([`fire-drill.md`](../disaster-recovery/fire-drill.md)). The drill restored `lldap`, `tinyauth` and `beszel-hub` with `deploy.yaml` and `restore.yaml`. Acceptable loss and downtime: Unknown; check [`exercises.md`](../disaster-recovery/exercises.md).

## Lifecycle

- Upgrade: bump the pinned image in the compose template and deploy. Unknown: whether a schema migration needs a backup first; check the lldap release notes before a major bump.
- Removal: removing it locks everyone out of Tinyauth-protected apps.
- Waits on `step-ca` for its first certificate; it tolerates a start without one by restarting.
