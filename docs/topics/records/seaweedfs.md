# SeaweedFS: Service Record

The on-site S3 store that every host's backups go to, running single-node on `storage`. The backup design that uses it is in [`backup.md`](../disaster-recovery/backup.md#storage-host); the catalog's facts are in the [coverage table](../disaster-recovery/coverage.md).

## Dependencies

- Needs the `caddy-proxy` network, the `data` volume and the rendered `s3-identity.json`, which holds the S3 keypairs generated by the `secrets` role. The `seaweedfs_bucket` role creates the bucket after it deploys.
- Needed by every `backup_agent` (writes), `cloud_sync` (reads, to relay to R2, B2 and OCI) and the restore path, which reads from it first ([`restore.md`](../disaster-recovery/restore.md)).

## Data

- The `homelab-backups` bucket: encrypted backup archives of every backed-up app. The archives are GPG-encrypted before upload ([`backup.md`](../disaster-recovery/backup.md#encryption)).
- `s3-identity.json` holds the S3 secret keys and is mode `0600`.

## Exposure

- The S3 API is routed through Caddy with `auth: false`, because a non-interactive S3 client cannot complete forward auth; access is by SigV4 keypairs. The filer web UI is routed behind Tinyauth and is read-only: Caddy answers anything but `GET` and `HEAD` with 405.
- Identities: one bucket-admin identity held only by `storage`, one narrow path-scoped identity per backup host, and one read-only bucket-wide identity for the cloud relay ([`backup-threat-model.md`](../disaster-recovery/backup-threat-model.md)).
- It keeps `CHOWN`, `SETUID` and `SETGID` for its entrypoint ([`adding-an-app.md`](../deploy/adding-an-app.md#container-hardening)).

## Threat model

- A compromised app host could try to read or delete other hosts' archives. Each host's identity is scoped to its own path and the archives are encrypted, so a reader of the bucket gets ciphertext ([`backup-threat-model.md`](../disaster-recovery/backup-threat-model.md)).
- Losing the host loses the on-site copy of every backup, which is why the cloud copies exist ([`cloud-sync.md`](../disaster-recovery/cloud-sync.md)).
- Unknown: whether the admin identity's key could be used from outside `storage`. Check the S3 route's network exposure.

## Observability

- The container health check requests the filer, and Beszel reports its state ([`beszel.md`](../monitoring/beszel.md)).
- The hourly backup freshness check pushes `backup-*` heartbeats and `cloud-sync` pushes its own, so a store that stops accepting or relaying archives raises a Gatus alert ([`gatus.md`](../monitoring/gatus.md)).

## Disaster recovery

Recovery tier 1. It has no `backup` entry: it is the backup target, and its archives are relayed to the clouds ([`cloud-sync.md`](../disaster-recovery/cloud-sync.md)). It is rebuilt beside the old VM, the bucket is copied across and DNS is flipped ([`rebuild-storage.md`](../disaster-recovery/rebuild-storage.md)). That was exercised on 2026-11-05; no archive was restored from the rebuilt store ([`fire-drill.md`](../disaster-recovery/fire-drill.md)). Acceptable loss and downtime: Unknown; check [`exercises.md`](../disaster-recovery/exercises.md).

## Lifecycle

- Upgrade: bump the pinned image in the compose template and deploy. Unknown: whether a version bump needs the bucket checked afterwards; the filer and S3 share one data directory.
- Removal: destroys the on-site copy of every backup. Do it only through the [storage rebuild](../disaster-recovery/rebuild-storage.md).
- Waits on nothing at start; everything that backs up waits on it.
